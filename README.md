> **8 место** на хакатоне PostCode Challenge от ПочтаТеха (сентябрь 2026), команда **innovibe**.
> Трек «Планирование команд и звёздная карта». Исходный репозиторий находился на платформе Codenrock;
> это публичная копия финальной версии решения (коммит `a67e404`).

> 🎬 Демо-видео: [`media/demo.mp4`](media/demo.mp4) · 📄 Подробная документация: [`docs/`](docs/), [`deliverables/`](deliverables/)

Сервис квартального планирования для руководителей команд, ресурсных менеджеров и ИТ-директора.
Загружает срез производственных данных, проверяет их качество, считает реальные ресурсы команд
и строит выполнимый план на шесть двухнедельных спринтов — с объяснением причин включения, переноса
и отмены работ. Раз в две недели принимает факт спринта и пересчитывает остаток квартала.
Звёздная карта показывает состав команд, компетенции, Bus Factor и работы, которые встанут без
единственного носителя компетенции.

Решение хакатона PostCode Challenge от ПочтаТеха.

Сервис состоит из двух частей:

- **`src/` — расчётное ядро.** Импорт и проверка датасета, точный планировщик (MILP, решатель HiGHS)
  с жадным запасным планом, причины решений, пересчёт по факту, риски, метрики, звёздная карта.
- **`orbit/` — сервер ОРБИТА.** Веб-интерфейс, учётные записи и права команд, согласования между
  главами, факт спринта, назначение конкретных людей на часы ролей. План строит ядро.

## Быстрый старт

Нужен Python 3.11 или новее.

**Запуск сервиса.** Проще всего — двойной щелчок по `orbit/start_windows.bat` (macOS и Linux:
`sh orbit/start.sh`). Скрипт создаёт окружение, ставит зависимости и открывает браузер. Нужен интернет
для установки пакетов.

Вручную, из корня репозитория:

```bash
python -m venv .venv
```

```bash
.venv\Scripts\activate
```

```bash
pip install -r requirements.txt
```

```bash
python orbit/app.py --open-browser
```

Первый запуск считает исходный план 7–10 секунд, дальше сервер поднимается за секунду: план
сохраняется в `orbit/var/orbit.db`. Интерфейс — http://127.0.0.1:8000.

**Вход для жюри.** Сервер создаёт учётные записи `jury-head` (глава Team-L с правом пересчёта
организации), `jury-platform` (глава Team-Platform — для согласований между командами) и `jury-member`
(сотрудник Team-L). Пароли — в `orbit/var/jury_access.txt`, подробности — в
[`docs/user-guide.md`](docs/user-guide.md).

### Проверка за 10 минут

1. Войти как `jury-head`: «Обзор» — 15 из 15 инициатив и 37 из 37 задач в квартале, ресурс команд,
   риски, разбор плана. «Стресс-сценарии» — что план перенесёт или предложит отменить при нехватке
   ресурса и почему.
2. «Задачи и спринты» — карточка любой задачи: решение, почему именно эти спринты, чьи часы.
3. «Звёздная карта» → «Риски компетенций»: Bus Factor ролей и технологий; «Проверить» у ENG-419
   (единственный Девопс) — какие цели уйдут за квартал без него.
4. Согласовать исходный план в обеих учётных записях глав (`jury-head` и `jury-platform`).
5. «Факт и пересчёт» → «Загрузить обновлённый датасет» → `data/samples/sprint1_deviations.xlsx` →
   «Итоговый пересчёт спринта 1»: выполнение спринта, отклонения и их последствия, красный, жёлтый
   и оранжевый риски, своя причина у каждого сдвига.
6. Войти как `jury-platform` → «Согласования»: передать KP-0000 в Team-L; согласовать как `jury-head` —
   PRODF-7120 возвращается в квартал.

Тот же сценарий одной командой, с отчётом: `python orbit/scripts/demo_scenario.py --out demo.md`.
Датасет после спринта по плану, без отклонений — `data/samples/sprint1_on_plan.xlsx` (выполнение 100 %).

**Первые шаги.** Сервер пишет путь к файлу `orbit/var/team_access.txt` с одноразовыми кодами глав
команд. Каждая глава регистрируется своим кодом и приглашает сотрудников из интерфейса. Право
пересчитывать прогноз всей организации выдаётся отдельно:

```bash
python orbit/app.py --grant-org-replan ЛОГИН_ГЛАВЫ
```

Подробно — в [`docs/user-guide.md`](docs/user-guide.md).

**Параметры запуска.** `python orbit/app.py` принимает:

| Параметр | Назначение |
|---|---|
| `--open-browser` | Открыть браузер, когда сервер готов |
| `--port 8001` | Другой порт, по умолчанию 8000 |
| `--db путь` | Другая база, по умолчанию `orbit/var/orbit.db` |
| `--host 0.0.0.0` | Доступ по сети — только за HTTPS-прокси, см. [`docs/user-guide.md`](docs/user-guide.md) |
| `--grant-org-replan ЛОГИН` | Выдать главе право пересчёта всей организации и выйти |
| `--revoke-org-replan ЛОГИН` | Отозвать это право и выйти |
| `--no-jury` | Не создавать учётные записи жюри `jury-head`, `jury-platform` и `jury-member` |

Состояние, учётные записи, коды глав и пароли жюри хранятся в `orbit/var/` — этот каталог не входит
в git.

**Расчёт без сервера** — консольный отчёт по данным, ресурсам и звёздной карте:

```bash
python -m src.main
```

**Тесты:**

```bash
python -m pytest tests
```

```bash
cd orbit && python -m pytest tests
```

Датасет один на обе части: `data/dataset.xlsx`, лист `Датасет(обновленный)`. Путь задан константой
`DATASET_PATH` в `src/dataset.py`.

## Исходные данные

Все шесть таблиц лежат на одном листе последовательно, друг под другом. Импортёр находит их
по тексту заголовка, а не по фиксированным номерам строк.

| Блок | Что содержит | Объём |
|---|---|---|
| `Tasks` | Задачи, инициативы, команды, статусы, оценки в очках и часах, скоринг `rung` | 45 задач, 15 инициатив |
| `Estimates` | Матрица трудозатрат: роли по строкам, задачи по столбцам | 258 ненулевых требований по 45 задачам |
| `Spent_time_roles` | Фактически затраченные часы по ролям для задач в работе | 24 записи, 602 часа |
| `Task_dependencies` | Связи между задачами | 19 строк |
| `Engineers_profiles` | Команды, роли, грейды, стек технологий, доступность | 34 строки, 30 инженеров |
| `Team_history` | Историческая производительность команд | 12 записей |
| Справочники | Варианты выбора цели работ, причины расхождения планов, результаты закрытия задачи | 8, 5 и 3 значения |

## Преобразования данных

**Поиск блоков.** Каждый блок находится по фрагменту заголовка (`Tasks (`, `Estimates.`,
`Task_dependencies` и так далее). Строка заголовков таблицы берётся следующей за названием блока,
данные читаются до начала следующего блока.

**Смета.** В исходном файле это широкая матрица: роли по строкам, задачи по столбцам. Она
разворачивается в таблицу вида `task_id | role | estimated_hours`. Строка «Итого по ролям»
исключается как не являющаяся ролью.

**Зависимости.** Заголовки блока смещены относительно данных, поэтому три колонки читаются
по позиции: блокирующая задача, блокируемая задача, тип связи.

**Даты.** Плановые и фактические даты задач хранятся в Excel числом дней от 30 декабря 1899 года
и приводятся к обычным датам. Фактическая дата завершения заполнена только у восьми закрытых задач.

**Стек технологий.** Поле `skills_declared` содержит перечень через запятую и разбирается в список
отдельных навыков — на нём строится звёздная карта. Всего в профилях 116 уникальных технологий.

**Справочники.** Три списка под таблицами читаются отдельно: варианты выбора цели работ, причины
расхождения планов заказчика и исполнителя, результаты работ при закрытии задачи. Они задают
допустимые значения статусов при переносе и отмене.

**Названия ролей.** Приводятся к единому виду по словарю `config/aliases.yaml`. Сейчас в нём три
пары: `ДевОпс` → `Девопс`, `Разработчик iOS` → `Разработчик IOS`, `Разработчик BigData` →
`Разработчик Big Data`. Без нормализации один и тот же специалист считался бы за двух разных.

### Обработка пропусков

| Ситуация | Как обрабатывается |
|---|---|
| Строка без `task_id` | Не считается задачей, отбрасывается |
| Пустое или нечисловое значение часов в смете | Приводится к нулю |
| Нулевые часы в смете | Требованием к роли не считаются, в выборку не попадают |
| Пустая роль в строке сметы | Строка отбрасывается |
| Пустые значения в паре «блокирующая — блокируемая» | Строка зависимости отбрасывается |
| Отсутствующий факт по роли | Остаток считается равным полной смете |

## Качество исходных данных

Валидатор ядра возвращает структурированный список проблем с кодом, уровнем и идентификатором
сущности. На текущем датасете ошибок нет, предупреждений 30. В сервисе список «Качество исходных
данных» шире: к ним добавляются перерасход часов по ролям (MP-102, SRV-4041), задача в работе
с исчерпанной сметой (MOB-7011), правило направления связей и диагностика плана — часы ролей вне штата.

| Уровень | Количество | Смысл |
|---|---|---|
| WARNING | 24 | Поле `estimated_hh` не совпадает с суммой часов по ролям в калькуляторе сметы |
| WARNING | 6 | Требуются роли, которых нет ни у одного инженера |

Источником трудозатрат считается сумма часов по ролям из калькулятора сметы. Поле `estimated_hh`
и строка «Итого по ролям» в расчётах не используются: в текущей версии датасета они расходятся
с суммой по ролям у 24 задач.

Это не сбои программы, а найденный дефицит исходных данных. Он отражается в рисках и объяснениях плана.

## Расчёт ресурсов

Очки и человеко-часы — независимые ограничения, проверяются совместно. Свободной ёмкости команды
недостаточно, если для задачи нет специалиста нужной роли.

```text
Ёмкость команды на спринт (SP) = средняя фактическая velocity × 0.8
Часы инженера на спринт        = 80 × capacity_rate
Остаток работ                  = смета по роли − факт по роли, отдельно по каждой роли
```

Остаток считается по каждой роли отдельно: перерасход одной роли не уменьшает объём работы другой.

| Команда | SP на спринт | SP на квартал | Часов на спринт |
|---|---|---|---|
| Team-Alpha | 10.8 | 64.8 | 240 |
| Team-Beta | 8.4 | 50.4 | 200 |
| Team-Delta | 7.6 | 45.6 | 200 |
| Team-K | 12.8 | 76.8 | 360 |
| Team-L | 8.0 | 48.0 | 960 |
| Team-Platform | 7.2 | 43.2 | 440 |

## Что показал анализ датасета

По 37 активным задачам (31 ToDo и 6 InProgress); SP задач в работе — по доле оставшихся часов:

| Показатель | Требуется | Доступно за квартал |
|---|---|---|
| Story Points | 222 | 329 |
| Человеко-часы (остаток работ) | 5 418 | 14 400 |

Суммарно всё помещается, но если брать специалистов строго из своей команды, 2 371 час из 5 418
выполнять некому. Дефицит делится на две части:

- **1 706 часов** — роль есть в компании, но в другой команде. Team-Platform требует 216 часов
  Java-разработчика и не имеет ни одного, Team-K требует 152 часа аналитика и не имеет ни одного.
- **665 часов** — роли нет ни в одной команде. Из них 449 часов приходятся на роль «Руководитель проекта».
  Такие роли требуются в 26 активных задачах из 37.

По очкам на пределе одна команда: Team-Platform, 42.1 SP спроса при 43.2 за квартал. Если считать задачи
в работе по полной оценке, спрос — 45 SP, и одна инициатива уходит за квартал.

Все 19 связей корректны и затрагивают 25 активных задач из 37, три связи межкомандные. Самая длинная
цепочка состоит из 3 задач при шести доступных спринтах. Узким местом являются часы конкретных ролей
и ёмкость Team-Platform, а не порядок выполнения.

## Допущения

Все расчётные допущения вынесены в `config/planner.yaml` и меняются без правки кода.
Обоснование каждого и открытые вопросы — в `docs/decisions.md`.

| Допущение | Значение | Основание |
|---|---|---|
| Коэффициент фокуса | 0.8 | Прямое указание онбординга |
| Часы полной ставки за спринт | 80 | Прямое указание онбординга, коэффициент фокуса уже учтён |
| Спринтов в квартале | 6 | Прямое указание онбординга |
| Направление связей | Первая задача блокирует вторую для всех трёх типов связи | Колонки таблицы названы `blocking_task_id` и `blocked_task_id`; онбординг описывает таблицу как граф «какая задача блокирует следующую» |
| Заимствование между командами | Разрешено с пометкой | Без него завершима одна инициатива из 15 |
| Роли, отсутствующие в компании | Выполняются вне штата, показываются риском «Роли вне штата» | Иначе план вырождается: 2 инициативы из 15 |
| Прогресс внештатных ролей | Идёт в той же доле, что работа штата | Их часов в факте нет; иначе спринт по плану давал бы меньше 100 % |
| Дата квартала | 5 октября — 27 декабря 2026 года | Ближайший квартал после последнего факта в датасете |
| Стабильность пересчёта | После фиксации базы — при любом пересчёте | План не перетасовывается из-за отпуска или помощи сильнее, чем нужно |

Все вопросы трактовки закрыты, решения и их основания — в `docs/decisions.md`.

## Принятые решения

Правила планирования, согласованные командой. Все значения — параметры планировщика
и меняются без правки кода.

| Решение | Значение | Почему |
|---|---|---|
| Основной сценарий (baseline) | `role_pool = team_borrow`, `missing_roles = external` | Строго внутри команды завершается 1 инициатива из 15, а если роли без носителей блокируют задачи — не больше 2. С таким baseline показатель квартала теряет смысл |
| Второй сценарий | `role_pool = team` | Показывает дефицит и причины вида «нет роли в команде» |
| Зазор зависимостей | `gap_planned = 1`, `gap_done = 0` | Онбординг: зазор минимум в спринт либо строго следующий спринт после фактического Done |
| Story Points в плане и метриках | Пропорционально прогрессу задачи; отдельного режима «зачёт при закрытии» нет | Ёмкость проверяется по долям прогресса. При зачёте в спринте завершения плановые SP спринта превышали бы ёмкость, а задача на 11 SP, сделанная как 7.15 + 3.85, давала бы 0 % и около 285 % выполнения при работе ровно по плану |
| Задачи в работе | `inprogress_sp = by_hours`: очки пропорционально остатку часов | У MOB-7011 остаток 0 ч из 165; полные 5 SP списывались бы за работу, которой уже нет. Режим `full` доступен параметром |
| Задачи в работе с нулевым остатком | Закрываются в спринте 1 без затрат очков и часов | Засчитываются в инициативу и открывают зависимые задачи по обычному правилу зазора; в журнал данных пишется предупреждение |
| Горизонт планирования | 12 спринтов, квартал — спринты 1–6 | Нужен для прогноза завершения и красного алерта |
| Знаменатель показателя квартала | Инициативы, запланированные к завершению в квартале | Формула считает инициативы из первоначального плана; частичная цель учитывается отдельно |
| Лестница целей | Инициативы, затем сумма rung, затем минимум заимствованных часов, затем максимум задач, затем прогноз | Каждый заимствованный час работает на спасение инициативы; задачи, которым хватает своих людей, всё равно попадают в план |
| Заимствования | Минимизируются только в квартале | После квартала план — прогноз; штраф за займ вытеснял бы отложенные задачи из прогноза |
| Решатель | HiGHS, один поток, нулевой допуск для целочисленных проходов, страховочный лимит 120 с | Повторяемость плана. Если лимит сработал, показывается жадный план со статусом `fallback_greedy`; повторяемость в этом случае не гарантируется |

Если в ответах организаторов о привлечении людей из других команд будет сказано иначе, меняется
только значение по умолчанию в конфигурации.

## Зачёт Story Points по факту спринта

Правила согласованы командой и реализуются вместе с пересчётом плана.

- **Базовые SP задачи** — те же, что в плане. При `inprogress_sp = by_hours` — остаток SP на момент baseline.
- **Плановые SP спринта** = сумма базовых SP задач × их доля в этом спринте по baseline. Считаются
  один раз и после пересчётов не меняются.
- **Прогресс открытой задачи за спринт** = фактические часы ролей штата / их остаток на начало
  спринта. Роли без носителей в штате в долю не входят и уменьшаются в той же доле. Пока задача
  не закрыта, накопленный прогресс не больше 0.9. Спринт, сделанный ровно по плану, даёт 100 %.
- **Задача закрыта в спринте** — засчитывается весь её остаток: базовые SP × (1 − накопленный прогресс).
- **Остаток для пересчёта** считается по каждой роли: остаток − факт, но не меньше 0. Если задача не закрыта,
  а часы кончились, остаток по каждой роли — не меньше 10 % сметы. Это допущение.
- **Выполнение плана спринта** включает все SP, сделанные в спринте, в том числе по задачам,
  которые в baseline стояли в других спринтах. Прогноз из пересчёта показывается отдельно от baseline
  и от факта.
- Для привычного Scrum-вида можно вывести информационную колонку «SP закрытых задач»; в показатель
  она не входит.

## Планировщик

### Как вызвать ядро из кода

Сервер вызывает ядро сам, этот раздел — для работы с ядром напрямую: сценарии, сравнения, отладка.

```python
from src.dataset import load_dataset
from src.planner import load_planner_config, run_scenario

config = load_planner_config()          # config/planner.yaml
plan = run_scenario(load_dataset(), config)
```

Параметры разделены на два типа. `InputConfig` меняет входные числа: очки задач в работе, ёмкости,
фонды, rung. `SolveConfig` меняет только правила выбора плана. Отсюда интерфейс:

```python
state = build_state(dataset, config.input)   # вход, собирается один раз
plan(state, config.solve)                    # план по правилам решения
```

Сценарии с разными правилами решения — `role_pool`, зазоры, режим цели — запускаются на одном состоянии
без пересборки. Передать во второй аргумент параметр, формирующий вход, невозможно: такого поля
в `SolveConfig` нет. В мете плана записаны оба конфига целиком, поэтому любой план можно воспроизвести.

### Модель простым языком

**Общая доля прогресса.** Каждая задача — это 100 % работы. В каждом спринте решатель выбирает, какую
долю задачи сделать. Эта доля одновременно списывает очки задачи из ёмкости команды и часы каждой роли
из фонда роли. Очки и часы друг в друга не пересчитываются — это два независимых лимита, общий у них
только прогресс задачи. Задача крупнее ёмкости спринта сама растягивается на несколько спринтов.

**Фонд роли по спринтам.** Фонд роли считается на каждый спринт отдельно. По умолчанию он одинаков
во всех спринтах — ставка × 80 часов по всем носителям роли. Сервер задаёт его точнее: инженер
в отпуске в третьем спринте не отдаёт часы в фонд своей роли в третьем спринте, а согласованная помощь
другой команде переносит часы из фонда одной команды в фонд другой ровно на свои спринты. Пример из
онбординга работает именно так: DB-202 требует 90 часов роли «Разработчик .net» при фонде 80 часов
в спринт — и растягивается на несколько спринтов.

**Потолок часов на спринт.** Человек с двумя ролями отдаёт часы в фонд каждой. Потолок суммы часов
по всем ролям за спринт — часы различных инженеров — не даёт потратить его дважды.

**Правила.** Работа идёт непрерывно и в каждом активном спринте не меньше 10 % задачи. Нельзя начинать
в квартале то, что в нём не закончится. Блокируемая задача начинается не раньше, чем через спринт после
завершения запланированной блокирующей, или сразу со следующего спринта после фактического Done.
Инициатива завершена, только если завершены все её задачи. Глава команды может запретить начинать
задачу раньше выбранного спринта.

**Предпроверка.** До решателя отсекаются задачи, невозможные при любом плане: нужной роли нет ни у кого
в выбранной области пула, работы больше, чем успеет роль до конца горизонта, или отменена блокирующая
задача. Такие задачи получают статус «отменена» с причиной.

**Лестница целей.** Решатель проходит уровни по очереди и закрепляет достигнутое на каждом:

1. Как можно больше завершённых инициатив, при равенстве — больше сумма rung.
2. Как можно меньше часов, взятых у других команд.
3. Как можно больше задач, завершённых в квартале. По желанию — при равном их числе закончить работу
   как можно раньше: без этого решатель волен растянуть задачи до конца квартала. Оба критерия решаются
   одним проходом со взвешенной суммой, как уровень 1. Сервер это правило включает, консольные
   сценарии по умолчанию — нет: на состоянии сервера оно поднимает время расчёта с 6 до 20 секунд.
4. Прогноз: отложенные задачи завершаются как можно раньше в пределах 12 спринтов.

Первые три уровня зависят только от квартала и решаются на модели из шести спринтов. Готовое расписание
квартала переносится на полный горизонт только для прогноза.

**Жадный план** строится всегда, по тем же правилам. Это запасной вариант на случай сбоя решателя,
база сравнения и нижняя граница: точный план не может завершить меньше инициатив, чем жадный.

**Проверка.** Любой план, жадный или точный, проверяется независимым валидатором, который не пользуется
моделью: ёмкости, фонды, доли, зазоры, статусы инициатив и наличие причин.

### Пересчёт по факту спринта

Раз в две недели загружается факт очередного спринта — таблица с колонками:

| Колонка | Смысл |
|---|---|
| `sprint` | Номер спринта от 1 до 6 |
| `task_id` | Идентификатор задачи |
| `role` | Роль, по которой списаны часы |
| `spent_hours` | Часы, затраченные в этом спринте |
| `status` | Статус на конец спринта: ToDo, InProgress или Done |

Строка без роли и часов допустима, если нужно сообщить только статус. Формат повторяет блок
`Spent_time_roles` исходного датасета, поэтому пользователю не приходится привыкать к новому.

```python
from src.planner.facts import load_sprint_fact
from src.planner.replan import replan
from src.store import make_baseline

baseline = make_baseline(first_plan)          # фиксируется один раз
fact = load_sprint_fact(table, dataset.role_aliases)
updated = replan(state, [fact], first_plan, baseline, config.solve)
```

Закрытые задачи уходят из модели, у остальных остаётся новый остаток по ролям, спринты до текущего
зафиксированы фактом. Включается уровень стабильности: план не перетасовывается без необходимости.
В результате появляется список изменений — спринт завершения в базе, в прошлом пересчёте и сейчас,
отдельно для задач и инициатив.

**База сравнения неизменяема.** Объект заморожен, план внутри хранится строкой и при каждом чтении
разворачивается в новую копию, файл на диске сохраняется только для чтения, а повторное сохранение
запрещено. Перед пересчётом и после него сверяется отпечаток базы; несовпадение параметров входа
с базой — ошибка, потому что сравнивать планы с разными правилами подсчёта очков нельзя.

### Сравнение с жадным планом

Оба движка работают по одним правилам и проверяются одним валидатором, поэтому сравнимы напрямую.
Замеры на текущем датасете:

| Сценарий | Жадный | Точный | Выигрыш | Секунд |
|---|---|---|---|---|
| Номинальная ёмкость | 13 | 15 | +2 | 1.8 |
| Ёмкость × 0.8 | 12 | 13 | +1 | 7.0 |
| Ёмкость × 0.6 | 9 | 11 | +2 | 8.3 |
| Ёмкость × 0.5 | 6 | 11 | +5 | 1.8 |
| Задачи в работе по полной оценке | 12 | 14 | +2 | 1.8 |
| Только своя команда | 1 | 1 | 0 | 0.0 |

Выигрыш растёт там, где ресурсов не хватает, — то есть ровно в ситуации пересчёта. Жадный план
считается за доли секунды и служит запасным вариантом: при сбое решателя или срабатывании
страховочного лимита в 120 секунд возвращается он, со статусом `fallback_greedy` и предупреждением.

```python
from src.planner.compare import compare_engines, format_comparison

print(format_comparison(compare_engines(dataset, scenarios)))
```

### Риски

Все алерты считаются из готового плана ядра (`src/risks.py`).

| Алерт | Вид | Когда возникает |
|---|---|---|
| Красный | `initiative_overrun` | Прогноз завершения инициативы за кварталом; названы мешающие задачи и первопричина. Если это была цель исходного плана — сказано и это |
| Жёлтый | `cascade_shift` | После пересчёта задача сдвинулась против базы и потянула зависимые задачи; названы цели цепочки |
| Жёлтый | `initiative_slip` | Цель ещё в квартале, но завершается позже базы; показан оставшийся запас |
| Оранжевый | `role_deficit` | В следующем спринте роль занята полностью, а готовая работа ждёт (или все носители отсутствуют); названы ждущие задачи и их цели |
| Оранжевый | `team_gap` | Команде в следующем спринте не хватает своих специалистов, план берёт часы у других команд без согласованной помощи |
| Оранжевый | `role_missing` | Роли без единого носителя: часы до конца квартала, работа вне штата |

Готовых работ больше фонда роли — это очередь, а не дефицит: дефицит, только когда роль занята
полностью и работа ждёт. Поэтому на исходном плане оранжевых рисков три, а не тринадцать.

Пример на официальных данных — спринт 1 с отклонениями (`data/samples/sprint1_deviations.xlsx`):

> **Красный.** Инициатива PRODF-7120 (rung 74) срывается: прогноз завершения — спринт 7 при квартале
> в 6 спринтов. По исходному плану она завершалась в спринте 3 — это квартальная цель. Мешают задачи:
> KP-3898. Причина: Team-Platform перегружена: 35.5 SP спроса при 34.9 за квартал.

> **Жёлтый.** Задержка SRV-4011 на 2 спринта сдвигает зависимые задачи: SRV-4010 (+2). Цели:
> PRODF-7126 — С6, в квартале.

### Причины решений

- **Включение:** цель и её rung, почему начало в этом спринте (зависимость, занятые SP команды или
  часы роли), почему задача растянута (SP больше ёмкости спринта, часов роли больше фонда),
  часы внештатных ролей и исполнители из других команд.
- **Перенос и отмена:** перегрузка команды или роли, контрфакт по запросу, прогноз и рекомендация —
  перенести, отменить или пересмотреть. У сорванной инициативы — первопричина и что делать с её
  работами в квартале (задел).
- **Изменения после пересчёта:** у каждой задачи своя причина — собственное отклонение, сдвиг
  блокирующей задачи, падение ёмкости команды с именем отставшей задачи или задача, занявшая её
  место в спринте. Итоги спринта показывают, что повлекло каждое отклонение.

### Стресс-сценарии и проверка отсутствия

«Стресс-сценарии» в разборе плана пересчитывают квартал при ёмкости на 20 % ниже (13 из 15 целей),
без внешних исполнителей (2 из 15) и без помощи между командами (1 из 15) — с решениями
и причинами по каждой перенесённой работе. «Что будет без сотрудника» на звёздной карте
пересчитывает план так, будто человек недоступен в выбранных спринтах. Оба расчёта ничего не сохраняют.

## Звёздная карта и Bus Factor

Способ расчёта (`src/star_map.py`):

- **Bus Factor роли** — число разных людей, у которых роль есть в профиле; совместитель нескольких
  команд считается один раз. Смета задачи задана в часах ролей, выполнить их может только носитель
  роли, поэтому при BF = 1 без этого человека встают все работы роли. Таких ролей восемь: без
  ENG-419 (единственный Девопс) под угрозой 13 целей из 15, без ENG-418 (архитектор) — 12.
- **Bus Factor технологии** — число людей, указавших её в стеке (`skills_declared`), по организации
  и внутри каждой команды. У 86 технологий из 116 один носитель.
- **Уникальные профили** — DBSCAN по наборам технологий: профили похожи, если косинусная близость
  не ниже 0.4. Уникальных — 17 из 30: у них нет коллеги с похожим стеком.
- **Доступность** — доля ставки × 80 ч с учётом отпусков и согласованной помощи.

Карта показывает команды, людей, совместителей и единственных носителей ролей (красная обводка);
профиль человека — роли, стек, доступность, задачи; профиль команды — ёмкость, покрытие ролей своими
людьми, часы других команд.

- **Ядро:** импорт всех шести блоков и справочников, нормализация ролей, проверка качества данных,

- **Сервер:** регистрация глав и сотрудников, права команд, план по спринтам с назначением конкретных

  спринта, разбор отклонений спринта, отчёт CSV, звёздная карта, право пересчёта всей организации.
- **Сервер считает всё ядром:** Excel читают импортёр и валидатор ядра, параметры берутся из
  `config/planner.yaml`, база — `make_baseline`, пересчёт по факту — со стабильностью и сравнением

На официальном датасете все 37 открытых задач и все 15 инициатив укладываются в 12 недель
(при условии внешних исполнителей для ролей вне штата). Точный план считается за 7–10 секунд.
Сценарий «отклонение → каскадный сдвиг → помощь → возврат в квартал» — `orbit/scripts/demo_scenario.py`
и шаги выше.

Ограничение: один проект на процесс. Для другого датасета или квартала — отдельный запуск с другой базой.

Ограничения устройства — в [`docs/architecture.md`](docs/architecture.md).

## Тесты

**Ядро**, `tests/`, 157 тестов, около двух минут:

- `tests/test_pipeline.py` — контрольные значения импорта, ресурсов и звёздной карты.
- `tests/test_planner_state.py` — вход планировщика и разделение параметров.
- `tests/test_planner_validate.py` — валидатор плана на маленьком выдуманном примере, где правильный
  ответ считается в уме; каждое правило нарушается по отдельности.
- `tests/test_planner_greedy.py` — жадный план во всех сценариях проходит валидатор.
- `tests/test_planner_milp.py` — точный план: число инициатив и сумма rung по сценариям, точность
  слитого прохода, неизменность состояния, повторяемость и воспроизводимость из меты, переход
  на жадный план при недопустимой модели.
- `tests/test_planner_explain.py` — причины переноса и контрфакты, включая бюджет на них.
- `tests/test_replan.py` — формат факта, пересчёт, неизменяемость базы и показатели.
- `tests/test_planner_compare.py` — точный план не хуже жадного.
- `tests/test_risks.py` — три алерта, включая каскадный сдвиг после пересчёта.
- `tests/test_orbit_bridge.py` — сквозной тест стыка: состояние сервера → вход ядра → план → независимый
  валидатор. Закрепляет числа постановки: ёмкость как средняя производительность × 0,8, 80 и 40 часов
  по ставке, зазор зависимостей, растяжение DB-202. Проверяет доступность по спринтам, передачу часов,
  требования технологий, ручной старт, потолок часов, назначение людей — в том числе закреплённого
  за работой человека, — звёздную карту, риски при нулевом фонде и полный цикл «база → факт → пересчёт»
  по правилам ядра.

```bash
python -m pytest tests
```

**Сервер**, `orbit/tests/`, 76 тестов, 2–6 минут: расчёт через ядро, права, сессии, согласования,
отчёты команд и загрузка обновлённого датасета, итоговый пересчёт спринта, отпуска и болезни,
CSV, риски и разбор плана ядра. Запросы к серверу пересчитывают план, отсюда время.

```bash
cd orbit && python -m pytest tests
```

Интерфейс проверяется без браузера — десять блоков проверок: разделы по ролям, формы, экранирование,
риски и разбор плана, данные спринта, отсутствия, звёздная карта:

```bash
cd orbit && python scripts/ui_fixture.py > ui-fixtures.json && node tests/ui_smoke.mjs ui-fixtures.json
```
