# Отчёт о работе: расчётное ядро `src/`

Период: 19–20 сентября 2026 года. Ветка `elina_task`, коммиты `7d68113`, `c43e8fe`, `f3590dd`.
Около 7 700 добавленных строк: код ядра, тесты, документация.

Отчёт описывает ядро в том виде, в каком оно было передано на сшивку с ОРБИТОЙ. Что изменилось
при сшивке — в [`report.md`](report.md).

## Задача

Построить расчётную основу сервиса квартального планирования:

- по датасету организаторов составить план на квартал из шести двухнедельных спринтов;
- объяснить, почему задача или инициатива не вошла в квартал;
- раз в спринт пересчитывать план по факту и сравнивать его с неизменной базой;
- показывать риски и показатели выполнения;
- проверять любой план независимо от того, как он построен.

## Итог

- Точный планировщик на целочисленной линейной модели (MILP, решатель HiGHS) с лестницей целей
  и прогнозом на 12 спринтов.
- Жадный план по тем же правилам: запасной вариант, база сравнения и нижняя граница.
- Независимый валидатор, предпроверка, причины переноса с контрфактами.
- Пересчёт по факту спринта с неизменяемой базой, список изменений, показатели выполнения.
- Три вида рисков.
- На датасете организаторов при номинальной ёмкости завершаются все 15 инициатив. Жадный план
  при тех же условиях завершает 13.
- 119 тестов, все зелёные, около двух минут.

### 2. Согласование правил

Прежде чем писать модель, составили перечень спорных трактовок данных и зафиксировали решения
в [`decisions.md`](decisions.md). Главные из них:

| Вопрос | Решение |
|---|---|
| Направление зависимостей | Любой тип связи: первая задача блокирует вторую |
| Зазор между связанными задачами | Один пустой спринт после запланированной блокирующей, ноль после Done |
| Ёмкость команды | Средняя производительность × 0,8 |
| Фонд часов | 80 часов на полную ставку за спринт, фокус 0,8 уже учтён |
| Роли без единого инженера | Не ограничивают план и выводятся риском |
| Часы из других команд | Разрешены, но их объём минимизируется |
| Очки задач в работе | Доля оценки по остатку часов |
| Минимальная работа в спринте | 10 % задачи в каждом активном спринте |
| Задача в работе с нулевым остатком | Закрывается в первом спринте без затрат |

Все правила вынесены в [`config/planner.yaml`](../config/planner.yaml) и меняются без правки кода.

### 3. Вход планировщика

Коммит `c43e8fe`, `src/planner/config.py`, `state.py`, `rules.py`.

Параметры разделены на два типа:

- `InputConfig` меняет входные числа: очки задач в работе, ёмкости, фонды, rung, длину квартала
  и горизонта;
- `SolveConfig` меняет только правила выбора плана: движок, пул ролей, зазоры, минимальную долю,
  контрфакты.

Состояние `PlanningState` собирается из датасета один раз. Разные правила решения запускаются
на нём без пересборки. В мете каждого плана записаны оба конфига целиком, поэтому любой план
можно воспроизвести.

### 4. Точная модель

Коммит `c43e8fe`, `src/planner/milp.py`.

**Общая доля прогресса.** Для каждой задачи и спринта решатель выбирает, какую долю задачи сделать.
Эта доля одновременно списывает очки из ёмкости команды и часы каждой роли из фонда роли. Очки
и часы друг в друга не пересчитываются: это два независимых лимита. Задача крупнее спринта сама
растягивается на несколько спринтов.

**Ограничения:** непрерывная работа, минимум 10 % за активный спринт, запрет начинать в квартале то,
что в нём не закончится, зазоры зависимостей, задачи в работе, завершение инициативы только вместе
со всеми её задачами.

**Лестница целей.** Уровни решаются по очереди, результат каждого закрепляется:

| Уровень | Цель | Где решается |
|---|---|---|
| 1–2 | Больше завершённых инициатив, при равенстве — больше сумма rung | Модель квартала, 6 спринтов |
| 3 | Стабильность: меньше перестановок относительно прошлого плана | Только при пересчёте |
| 4 | Меньше часов, взятых у других команд | Только спринты квартала |
| 5 | Больше задач, завершённых в квартале | Модель квартала |
| 6 | Прогноз: отложенные задачи завершаются как можно раньше | Полный горизонт, 12 спринтов |

Уровни 1 и 2 слиты в один проход: вес инициативы равен сумме всех rung плюс один, плюс её собственный
rung. Поэтому одна лишняя инициатива всегда весит больше любой разницы в rung, и решение совпадает
с двумя отдельными проходами. Уровни 1–5 решаются на модели из шести спринтов, готовое расписание
квартала переносится на полный горизонт и там закрепляется для прогноза.

**Решатель.** PuLP 3.3.2 и HiGHS 1.15.1 с фиксированными версиями, один поток и фиксированное зерно,
поэтому результат повторяется. Страховочный лимит — 120 секунд. При сбое решателя или превышении
лимита возвращается жадный план со статусом `fallback_greedy` и предупреждением. Решатель CBC
отвергнут: с нулевым зазором оптимальности он работал непрактично долго.

### 5. Жадный план, предпроверка, валидатор

Коммит `c43e8fe`, `greedy.py`, `precheck.py`, `validate.py`.

- **Предпроверка** до решателя отменяет задачи, невозможные при любом плане: нужной роли нет
  ни у кого, работы больше, чем роль успеет до конца горизонта, отменена блокирующая задача.
  Отмена каскадом проходит по цепочке, у каждой задачи своя причина.
- **Жадный план** размещает задачи по приоритету инициатив в самый ранний допустимый спринт
  по тем же правилам. Он строится всегда и служит нижней границей: точный план не может завершить
  меньше инициатив.
- **Валидатор** не пользуется моделью и проверяет готовый план заново: полноту набора задач,
  доли, ёмкости команд, фонды ролей, зазоры, статусы инициатив, заимствования, наличие причин.
  Через него проходит любой план, жадный или точный.

### 6. Причины и контрфакты

Коммит `c43e8fe`, `explain.py`, `assemble.py`, `result.py`.

У каждой перенесённой задачи и незавершённой инициативы есть причина простым языком: отменена
предпроверкой, ждёт блокирующую задачу, не хватает ёмкости команды или фонда роли, с указанием
загрузки.

**Контрфакт** отвечает на вопрос «что будет, если взять это в квартал принудительно». Модель
решается ещё раз с обязательным завершением выбранной инициативы. Ответ показывает цену: например, в сценарии,
где задачи в работе считаются по полной оценке, принудительное завершение PRODF-7120 вытесняет
PRODF-7121. Контрфакты ограничены бюджетом:
не больше 10 решений за 20 секунд.

В результат плана также входят загрузка команд и ролей по спринтам, узкие места, таблица
заимствований и спрос на следующий спринт.

### 7. Пересчёт по факту и неизменяемая база

Коммит `c43e8fe`, `facts.py`, `replan.py`, `src/store.py`, `src/metrics.py`.

- **Факт спринта** — таблица в формате блока `Spent_time_roles` исходного датасета: спринт, задача,
  роль, часы, статус. Проверяются порядок спринтов, известные задачи и роли.
- **Пересчёт** убирает закрытые задачи, пересчитывает остаток по ролям, фиксирует прошедшие
  спринты и включает уровень стабильности.
- **Список изменений** — спринт завершения в базе, в прошлом пересчёте и сейчас, отдельно для задач
  и инициатив.
- **Зачёт очков по факту**: прогресс по часам ограничен 90 %, пока задача не закрыта; если часы
  по оценке исчерпаны, а задача не закрыта, остаётся 10 %.
- **База неизменяема.** Объект заморожен, план внутри хранится строкой и при чтении разворачивается
  в новую копию, файл сохраняется только для чтения, повторное сохранение запрещено. До и после
  пересчёта сверяется отпечаток базы. Пересчёт с другими параметрами входа, чем у базы, — ошибка.
- **Показатели:** выполнение спринта и квартала по очкам, задачам и инициативам относительно базы.

### 8. Сравнение движков

Коммит `c43e8fe`, `compare.py`. Оба движка работают по одним правилам и проверяются одним
валидатором, поэтому их можно сравнивать напрямую.

| Сценарий | Жадный | Точный | Выигрыш |
|---|---|---|---|
| Номинальная ёмкость | 13 | 15 | +2 |
| Ёмкость × 0,8 | 12 | 13 | +1 |
| Ёмкость × 0,6 | 9 | 11 | +2 |
| Ёмкость × 0,5 | 6 | 11 | +5 |
| Задачи в работе по полной оценке | 12 | 14 | +2 |
| Только своя команда | 1 | 1 | 0 |

Число — завершённые в квартале инициативы из 15. Выигрыш точной модели растёт там, где ресурсов
не хватает, то есть именно в ситуации пересчёта. Точный план считается не дольше 9 секунд.

### 9. Риски

Коммит `f3590dd`, `src/risks.py`. Все алерты считаются из готового плана без отдельных расчётов.

| Алерт | Когда возникает |
|---|---|
| Красный | Инициатива не завершается в квартале: прогноз завершения позже шестого спринта |
| Жёлтый | После пересчёта задача сдвинулась и потянула цепочку зависимых работ |
| Оранжевый | По роли готово больше работ, чем она успевает, или роли нет ни у кого |

У жёлтого показывается корень каскада и все задачи ниже по цепочке. Оранжевый сообщает, на сколько
спринтов очередь и выходит ли она за квартал.

> **Красный** (сценарий с полной оценкой задач в работе). Инициатива PRODF-7120 (rung 74) срывается: прогноз завершения — спринт 8 при квартале
> в 6 спринтов. Мешают задачи: ASUKD-5918, KP-0000, KP-3898.

### 10. Звёздная карта

Коммит `c43e8fe`, `src/star_map.py`.

- Совместитель записан в таблице по разу на каждую команду. Теперь строки сводятся к одной на
  человека, иначе его навыки считались дважды: 34 строки дают 30 людей.
- **Bus Factor** — подсчёт: сколько разных людей владеет навыком. Навыков, которые знает один
  человек, — 86 из 116.
- **Уникальные специалисты** — DBSCAN по наборам навыков, косинусное расстояние, `eps=0.3`,
  `min_samples=2`. Уникальным отмечается человек, у которого нет ни одного коллеги с похожестью
  набора навыков от 0,7. Это показывает, кем заменить человека целиком, а не по одному навыку.

### 11. Подготовка к сшивке с ОРБИТОЙ

- Проведён аудит параллельного проекта `orbit/`. Его планировщик и импорт не взяты: на датасете
  он завершал 4 задачи из 45 и 1 инициативу из 15, связи читал в обратную сторону, не соблюдал
  зазор, связывал очки с часами, а импорт молча терял данные. Взяты учётные записи, права,
  согласования, заявки, навыки, доступность, назначение людей, факт в CSV и интерфейс.
- Перечислены обязательные исправления сервера: закрытие соединений SQLite, право на пересчёт,
  блокировка по проекту вместо общей, отказ от падения при ошибке проверки плана, синхронные
  пересчёты в восьми местах.
- Написан `handoff.md`: контракт ядра, вердикт по ОРБИТЕ, порядок сборки. Первым шагом
  сборки поставлен сквозной тест «состояние сервера → адаптер → план → валидатор ядра».
