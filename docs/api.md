# HTTP API сервера ОРБИТА

Приложение обслуживает интерфейс и API с одного origin. Все пути `/api`, кроме health и auth/status/login/register, требуют сессию. Проект определяется учётной записью; выбирать чужой проект параметром адреса нельзя.

При входе и регистрации сервер выдаёт HttpOnly, SameSite=Strict cookie `orbita_session` и возвращает `{user, csrf}`. В `user` есть `org_replan` — право пересчитывать прогноз всей организации. В последующих POST передавайте `X-CSRF-Token`, cookie и JSON (`Content-Type: application/json`). Чужой Origin запрещён. Сессия действует 12 часов. У пользователя одна активная сессия: успешный повторный вход атомарно отзывает все его прежние cookie и выдаёт новый CSRF-токен. Старая cookie возвращает 401; неудачный вход текущую сессию не отзывает. Для HTTPS включается `ORBIT_COOKIE_SECURE=1`.

Изменяющие план операции требуют актуальный `revision`; необязательный `project_id` должен совпадать с проектом пользователя. Результат — отфильтрованное состояние интерфейса. `preview:true` возвращает только расчёт и не сохраняет состояние.

| Метод и путь | Данные / результат | Доступ |
|---|---|---|
| GET `/api/health` | `{status, version}`, версия сейчас 3.0.0 | Все |
| GET `/api/auth/status` | `{teams:["Team-L", ...]}` — только имена команд, без признака регистрации | Все |
| POST `/api/auth/register` | `login, name, password, code, role` | Одноразовый код |
| POST `/api/auth/login` | `login, password` | Все |
| GET `/api/auth/me` | `user, csrf` | Сессия |
| POST `/api/auth/logout` | `{}` | Сессия + CSRF |
| GET `/api/state` | Задачи, люди, план; объём зависит от роли | Сессия |
| GET `/api/report.csv` | Одна CSV-таблица доступных задач | Сессия |
| POST `/api/invitations` | `revision, engineer_id` → одноразовый код | Глава своей команды |
| POST `/api/tasks/add` | `revision, task_id?, title, initiative, sp, hours, priority?, predecessors?` | Глава своей команды |
| POST `/api/tasks/update` | `revision, task_id, changes, preview?` | Глава команды задачи |
| POST `/api/employees/add` | `revision, name, roles[], skills[], capacity_rate, grade?` | Глава своей команды |
| POST `/api/employees/absence` | `revision, engineer_id, start, end` (ГГГГ-ММ-ДД включительно), `reason` (Отпуск, Болезнь, Обучение, Другое), `comment?`, `preview?` → план пересчитан; с `preview` — `{lost, changes, risks}` без сохранения | Глава команды сотрудника |
| POST `/api/employees/absence/delete` | `revision, absence_id` → план пересчитан | Глава команды сотрудника |
| POST `/api/employees/availability` | `revision, engineer_id, hours:{"1":40,...}` | Глава единственной команды сотрудника |
| POST `/api/requests/create` | `revision, proposal, comment?, preview?` | Глава участвующей команды |
| POST `/api/requests/decide` | `revision, request_id, decision` | Одна из двух глав |
| POST `/api/approve` | `revision` → голос за исходный план | Все зарегистрированные главы последовательно |
| POST `/api/replan` | `revision` | Глава с правом `org_replan` |
| POST `/api/explain` | `{}` → `{tasks, initiatives}` — подробный разбор с контрфактами, 20–40 с; план не меняет | Глава + CSRF |
| GET `/api/facts/template.csv` | Шаблон только своей команды | Глава |
| POST `/api/facts/parse-csv` | Сырые байты CSV, `Content-Type: text/csv` → `{report}` | Глава + CSRF |
| POST `/api/facts` | `revision, report` — отчёт команды об итогах спринта, без пересчёта | Глава своей команды |
| POST `/api/dataset/upload` | Байты xlsx, `Content-Type` таблицы Excel, заголовки `X-Revision` и необязательный `X-Sprint` → состояние; план не пересчитывается | Глава с правом `org_replan` + CSRF |
| POST `/api/sprint/close` | `revision, sprint` — итоговый пересчёт спринта | Глава с правом `org_replan` |

`changes` поддерживает `priority`, `remaining_sp`, `remaining_hours` (роль → часы), `required_skills` (роль → список), `assignments` (роль → engineer_id), `not_before` (незакрытый спринт до конца горизонта). `team` нельзя изменить этим методом.

Варианты `proposal`:

```json
{"kind":"transfer","task_id":"ONK-2914","to_team":"Team-Alpha"}
```

```json
{"kind":"exchange","task_id":"ONK-2914","to_team":"Team-Alpha","other_task_id":"MOB-7012"}
```

```json
{"kind":"help","from_team":"Team-L","to_team":"Team-Alpha","engineer":"ENG-401","hours":16,"start":1,"end":6}
```

Это примеры формы запроса: задачи, роли и свободные часы проверяются по текущему состоянию. `decision`: `approve`, `reject`, `refresh`. Устаревшее согласование не применяется. При обмене обе передачи сохраняются одной версией.

`report` содержит `sprint` (номер спринта квартала), `achieved_sp`, `note` и `tasks`: полный набор незавершённых задач своей команды. Элемент задачи содержит `task_id, status, remaining_sp, remaining_hours, spent_hours`. `remaining_sp` и `remaining_hours` можно передать `null`: тогда остаток считается правилом ядра — прежний остаток роли минус потраченные часы, а если часы кончились, а задача не закрыта, — 10 % сметы; очки уменьшаются в той же доле. Шаблон CSV выдаёт остатки пустыми. Отчёты сохраняются по командам и план не пересчитывают. Повтор неизменённого отчёта с актуальной revision не создаёт новую версию.

Ошибки: 400 — неверные данные; 401 — требуется вход; 403 — нет прав или неверный CSRF; 404 — неизвестная операция; 409 — устаревшая версия/заявка; 413 — размер запроса больше 2 МБ; 415 — неверный Content-Type. В ответе `{error: "описание"}`.

Старые общедоступные `/api/plan`, `/api/actuals`, `/api/scenario/accept`, `/api/import` удалены и отвечают 404. `Service` не проверяет права: HTTP-маршруты используют `TeamService` и `Auth`.

У каждой видимой задачи в `/api/state` есть `history` — архив плановых фрагментов закрытых спринтов, и `facts` — подтверждённые результаты задачи по спринтам. `entry.fragments` содержит будущие назначения. История возвращается только для задач, доступных текущему пользователю. CSV объединяет архивные и будущие плановые SP; фактические часы выгружаются отдельными столбцами.

## Данные спринта и итоговый пересчёт

`POST /api/dataset/upload` принимает обновлённый датасет в формате исходного. Без `X-Sprint` он относится к текущему спринту; `X-Sprint` равный последнему закрытому спринту — исправление этого спринта. До фиксации базы датасет заменяет исходные данные, план помечается `plan_stale` и пересчитывается `POST /api/replan`; пока план устарел, `/api/approve` отвечает 400.

`POST /api/sprint/close` собирает факт спринта из загруженного датасета и отчётов команд и один раз пересчитывает план. По задачам из датасета статус, потраченные за спринт часы (накопленные в датасете минус уже учтённые) и остаток берутся из него; по остальным — из отчёта команды или без изменений. SP команды — новая строка `Team_history`, иначе отчёт главы; если нет ни того, ни другого — 400 со списком команд. Датасет сливается с данными проекта: новые задачи и сотрудники добавляются, у существующих обновляются оценки и описание, отсутствующие остаются; команда задачи, сменённая согласованной заявкой, сохраняется.

Для главы `/api/state` содержит `sprint_data` — `current` (текущий спринт) и `correction` (новая загрузка за последний закрытый спринт): сводка датасета, источники данных по командам и задачам, `missing_teams`, расхождения датасета с отчётами, `ready`. `reviews` — итоги закрытых спринтов: `deviations` (задача, команда, текст отклонения), `goals_lost`, `goals_gained`, изменения производительности. `plan_stale` — план не пересчитан после новых исходных данных.

## Согласование исходного плана

`POST /api/approve` с актуальной `revision` сохраняет согласие текущей главы. Пока согласились не все зарегистрированные главы проекта, `baseline` остаётся `false`. Последнее согласие и исходная база сохраняются **одной версией**. Если зарегистрирована одна глава, достаточно её согласия. Повтор уже учтённого голоса с актуальной revision не создаёт новую версию; после фиксации повторная фиксация возвращает 400.

До фиксации `/api/state` главы включает `baseline_approval`: `required`, `confirmed`, `own_approved`, `stale`, `heads:[{team,name,approved}]`. После фиксации и для сотрудника это поле равно `null`. Изменение условий/плана или состава зарегистрированных глав обнуляет действующие согласия; `stale:true` сообщает об этом. Следующий `/api/approve` начинает сбор для актуального состояния. Неизменённый детерминированный пересчёт, создание заявки и регистрация сотрудника сами по себе согласия не сбрасывают.

`POST /api/replan` пересчитывает прогноз всей организации, поэтому одной роли главы для него мало: нужно право `org_replan`, без него — 403. Право выдаёт владелец установки командой `python app.py --grant-org-replan ЛОГИН` и отзывает `--revoke-org-replan`. Пересчёт записывается в историю как организационное действие с командой и именем инициатора. В `/api/approve` и `/api/replan` разрешены только `revision` и необязательный `project_id`; передать `config` нельзя. Глава по-прежнему читает всю организацию, а меняет задачи, сотрудников и факт своей команды. Сотрудник видит также личное назначение в другой команде при согласованной помощи.

## Регистрация и пароль

Пароль — строка длиной 10–256 символов. Пароль только из цифр или равный логину (без учёта регистра и пробелов по краям) отклоняется с 400 до расходования приглашения. Например, `1234567890` недопустим; `Long-password-42` подходит по правилам. Проверка действует при новой регистрации; уже существующие аккаунты и хэши не изменяются. Команда и роль задаются кодом приглашения; выбранная в форме роль должна соответствовать коду.

JSON принимает media type `application/json`, в том числе с `; charset=utf-8`. `application/jsonp` возвращает 415, `NaN`/`Infinity`/`-Infinity` — 400. Неожиданные ошибки GET/POST возвращают 500 с JSON `{error}` без внутренних деталей.

## План в ответе

У каждой задачи в `/api/state` есть `entry`: `status` (`done`, `planned`, `beyond`, `partial`, `blocked`), `start`, `end`, `reasons` и `fragments` — доли работы по спринтам с очками и исполнителями. Задача может занимать несколько спринтов: ядро считает долю работы в каждом, а не «задачу целиком в спринте».

В плане также есть `validation` — нарушения независимой проверки ядра (на исправном плане пусто) и `engine` — каким движком построен план: `optimal` для точного решения, `fallback_greedy`, если решатель не справился и показан жадный план; `stability: true` — план пересчитан после факта спринта с уровнем стабильности ядра.

Для главы `/api/state` дополнительно содержит:

| Поле | Содержимое |
|---|---|
| `risks` | Алерты ядра `src/risks.py`: `{level, kind, subject, text, details}`. `level` — `red` (инициатива не завершается в квартале), `yellow` (задержка задачи сдвинула зависимые, после фиксации базы), `orange` (спрос готовых работ роли на следующий спринт больше фонда или роли нет в штате) |
| `analysis` | Разбор плана ядра: `bottlenecks` — ограничения на 100 %, `borrowing` — часы роли сверх фонда команды, `demand` — спрос на следующий спринт против фонда, `engines` — сравнение точного и жадного плана по тем же условиям |
| `metrics` | Показатели `src/metrics.py`: `goal_count` — инициативы, которые база завершает в квартале; `actual_done`, `forecast_done` и проценты; `sprints[]` — `planned` (SP базы), `actual` (зачтено по часам и закрытиям), `percent`, `reported` (SP, заявленные главами, для сверки), `by_team` |
| `star` | Звёздная карта ядра `src/star_map.py` по текущему составу: `bus_factor[]` — технология, число носителей по организации и их ID; `unique` — профили, не попавшие ни в одну группу DBSCAN |

План ядра целиком хранится в каждой версии (поле `plan.core`, сжатый JSON без времени расчёта) — по нему строятся база сравнения, пересчёт со стабильностью и показатели.

Изменяющий запрос отвечает только после пересчёта плана. Это до 35 секунд, если изменение меняет модель, и мгновенно, если те же условия уже считались.
