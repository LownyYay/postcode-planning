# Отчёт о работе: перевод ОРБИТЫ на расчётное ядро `src/`

Период: 20–21 сентября 2026 года. Ветка `elina_task`, 14 коммитов, 65 файлов, +3 974 / −1 695 строк.

## Задача

В репозитории было два проекта, которые считали план каждый по-своему:

- **`src/`** — расчётное ядро: импорт и проверка датасета, точный квартальный планировщик (MILP, решатель HiGHS), причины решений, пересчёт по факту, риски, метрики, звёздная карта. Интерфейса нет.
- **`orbit/`** — веб-сервис ОРБИТА: учётные записи, права команд, согласования между главами, факт спринта, интерфейс. Свой упрощённый планировщик.

Цель — сделать ядро единственным источником расчётов, сохранив интерфейс, права, согласования, заявки, навыки, доступность и назначение людей. Затем привести репозиторий в порядок и перенести в ОРБИТУ всё, что реализовано в ядре.

## Итог

- ОРБИТА больше не считает сама: план, пересчёт, база, показатели, риски, звёздная карта и разбор Excel — функции ядра.
- Один датасет, один конфиг, одно окружение, один список зависимостей, одна документация в `docs/`.
- На официальных данных: 34 из 37 открытых задач завершаются в квартале, 14 из 15 инициатив. Жадный план по тем же условиям даёт 12 инициатив.
- Тесты: ядро — 146, сервер — 71, плюс проверка интерфейса без браузера. Всё зелёное.

## Этапы

### 1. Ядро научилось понимать ограничения сервера

Коммит `a4e6fb6`. Ядро считало по ролям и ничего не знало о людях, отпусках, навыках и передаче часов. Новых сущностей в ядро не добавляли — всё выражено через фонды часов:

| Что задаёт глава | Как это видит ядро |
|---|---|
| Доступность человека по спринтам | Фонд роли команды на конкретный спринт (`sprint_role_fund`) |
| Согласованная передача часов | Тот же фонд: часы уходят из одной команды в другую на интервал спринтов |
| Требование технологий к задаче | Производная роль, например `Разработчик .net (Python)` |
| Ручное назначение исполнителя | Производная роль с одним носителем: `Разработчик Java (ENG-401)` |
| Человек с несколькими ролями | Потолок часов на спринт (`hours_limit`), чтобы часы не потратились дважды |
| «Не раньше спринта N» | Ранний старт задачи (`not_before`) |

Изменения прошли через все части ядра: вход, предпроверку, жадный план, MILP, разбор причин, сборку плана, валидатор, риски.

### 2. Адаптеры и сквозной тест стыка

Коммиты `9273900`, `19314c8`.

- `orbit/planner/bridge.py` — состояние ОРБИТЫ → вход ядра.
- `orbit/planner/present.py` — план ядра → план ОРБИТЫ: доли задачи по спринтам превращаются во фрагменты интерфейса, часы ролей раскладываются на конкретных людей потоком Эдмондса — Карпа.
- `tests/test_orbit_bridge.py` — сквозной тест: состояние сервера → адаптер → план → независимый валидатор. Сервер и интерфейс не трогали, пока он не прошёл. Тест закрепляет числа постановки: ёмкость команды как средняя производительность × 0,8, 80 часов на полную ставку, зазор зависимостей, растяжение DB-202 на несколько спринтов.

### 3. Правило «как можно раньше»

Коммит `5730558`. Без него 23 задачи из 34 заканчивались в шестом спринте, и у зависимых работ не было запаса. Правило разрывает ничью между равноценными планами и на число инициатив и задач не влияет. Сначала пробовали отдельный проход с ограничением по времени (нарушал повторяемость) и непрерывную цель (20 секунд). Остановились на взвешенном слиянии с уровнем задач, включаемом параметром `early_finish`.

### 4. Замена движка

Коммиты `92e44f8`, `ec06f3e`.

- Расчёт сервера переведён на ядро, собственный планировщик ОРБИТЫ удалён.
- Результат ядра кэшируется по отпечатку условий: повторный расчёт тех же условий — сотые доли секунды.
- Неудачный расчёт не роняет сервер, а возвращается планом с пометкой.
- Исправлена утечка соединений SQLite: на Windows незакрытые соединения блокировали файл базы.

### 5. Производительность и права

Коммиты `0504d5d`, `d24b9c9`, `c72fd6b`.

- Точный расчёт занимает 13–20 секунд при первом запуске и до 35 секунд после изменения состава. Время сохранили ради правила «как можно раньше», но сделали работу видимой: интерфейс показывает счётчик секунд.
- Замок на проект вместо общего: изменения одного проекта идут по очереди, чтение замок не берёт.
- Право `org_replan` на пересчёт всей организации. Выдаётся и отзывается командой запуска `--grant-org-replan` / `--revoke-org-replan`; без него кнопки нет, прямой запрос отвечает 403.
- Исправлен запуск: зависимости `pulp` и `highspy`, путь импорта ядра, Docker-образ собирается из корня.

### 7. Один парсер и один конфиг

Коммит `fc234e7`.

- ОРБИТА читает Excel импортёром ядра и проверяет данные валидатором ядра; свой парсер удалён. Результат совпал со старым поле в поле, кроме написания одной роли по словарю `config/aliases.yaml`.
- Длина квартала, горизонт, коэффициент фокуса, часы ставки и правила решения читаются из `config/planner.yaml` — того же файла, что у консольного расчёта.

### 8. Пересчёт, база, показатели и риски по правилам ядра

Коммит `0c5660a`.

| Что | Функция ядра |
|---|---|
| Исходная база: квартальные цели и плановые SP | `src/store.make_baseline` |
| Пересчёт после факта со стабильностью | `src/planner/replan.rescale_previous` |
| Изменения относительно базы | `src/planner/replan.plan_changes` |
| Остаток задачи, если глава его не указала | Правило `src/planner/facts.py`: прежний минус потраченное, не меньше 10 % сметы |
| Выполнение спринта и квартала | `src/metrics.py` |
| Красный, жёлтый и оранжевый алерты | `src/risks.find_risks` |

План ядра хранится в каждой версии ОРБИТЫ сжатым JSON. SP, заявленные главами, по-прежнему обновляют производительность команд и показываются рядом с зачётом ядра.

### 9. Интерфейс

Коммит `eedda81`.

- Обзор главы: риски плана с цветом, разбор плана — узкие места, заимствования, спрос на следующий спринт, сравнение точного и жадного плана.
- «Подробный разбор» — контрфакты ядра по запросу («что будет, если включить эту задачу»), 20–40 секунд, план не меняет.
- Таблица «План и факт»: зачтённые по правилам ядра SP и отдельно SP, заявленные командами.
- Звёздная карта: Bus Factor по организации и уникальные профили по кластеризации DBSCAN.
- Форма факта: остатки можно не заполнять.

## Найденные и исправленные ошибки

| Ошибка | Причина | Исправление |
|---|---|---|
| Плавающий тест ручного назначения падал примерно в каждом третьем прогоне | Люди раскладывались по одной задаче, первым брался меньший ID. Новый сотрудник получает случайный ID; если он меньше `ENG-401`, его часы забирала другая Java-задача | Один поток на весь спринт с досчётом по приоритету. Тест с таким ID падает на старом коде и проходит на новом |
| Деление на ноль в оранжевом алерте ядра | Все носители роли недоступны в спринте, фонд равен нулю | Отдельная формулировка «роль недоступна в этом спринте» |
| Неверный фонд роли на квартал в ядре | Считался как «фонд спринта × число спринтов», хотя фонд меняется по спринтам | Сумма по спринтам |
| При замыкании команд на себя отменялась 31 задача из 37 | Шесть ролей есть не в каждой команде | Режим `team_borrow`: специалисты общие, заимствования видны отдельно |
| 58 ложных нехваток часов | Роли без единого носителя раскладывались на людей | Такие работы выполняются вне штата и показываются диагностикой |
| Согласия глав сбрасывались при повторном расчёте тех же условий | В план попадало время расчёта | Время из сохраняемого плана убрано |
| Закреплённого инженера забирали другие задачи | Порядок раскладки не учитывал узость круга исполнителей | Сначала работы с самым узким кругом, затем общий поток |
| Сбой регистрации после добавления права `org_replan` | Вставка без списка колонок | Явный список колонок и миграция старых баз |

## Известные ограничения

- Задачи, добавленные после фиксации базы, в зачёт SP спринта не входят: плановых SP для них нет.
- Контрфакты считаются без уровня стабильности; после факта спринта их план может немного отличаться от показанного.
- Два ручных назначения на одного человека в одном спринте ядро не запрещает; при раскладке одно останется без часов.
- Один проект на процесс сервера; для другого датасета — отдельный запуск с другой базой.
