# Решения по трактовке данных и правилам расчёта

Условия задачи и онбординг оставляют часть правил на усмотрение команды. Здесь — каждое такое
решение: что говорят данные, какой вариант принят и почему, где он живёт в конфигурации.
Параметры в `config/planner.yaml` меняются без правки кода; раздел указан в скобках.

Сводная таблица — в конце документа. Краткая версия — в разделах «Допущения» и «Принятые решения»
файла `README.md`.

## 1. Направление связей между задачами

**Вопрос.** Таблица `Task_dependencies` содержит три типа связей: `has to be done before`,
`is required for`, `depends on`. Читаются ли они в одну сторону?

**Данные.** Колонки называются `blocking_task_id` и `blocked_task_id` — направление задано самой
структурой. Онбординг описывает таблицу как граф «какая задача блокирует следующую». Проверка на фактах:
завершённая задача не может ждать незавершённую. При чтении «первая блокирует вторую» противоречие
одно — `KP-3898 → ASUKD-5222` (показано предупреждением в качестве данных), при развороте `depends on`
и `is required for` — шесть.

**Решение.** Для всех трёх типов первая задача блокирует вторую. Параметра нет: так читает импортёр.

## 2. Зазор между связанными задачами

**Данные.** Онбординг требует зазор минимум в один спринт, либо блокируемая задача ставится строго
в следующий спринт после фактического завершения первой.

**Решение.** Два параметра: `gap_planned = 1` — если блокирующая только запланирована, между ними
один пустой спринт; `gap_done = 0` — после фактического Done блокируемая начинается со следующего
спринта (`solve.gap_planned`, `solve.gap_done`).

## 3. Специалисты других команд

**Данные.** Из 5 418 часов остатка активных работ 2 371 приходится на роли, которых нет в своей
команде; из них 1 706 часов — роли, которые есть в другой команде (Team-Platform нужен
Java-разработчик, Team-K — аналитик).

**Решение.** Специалисты организации общие, но часы, взятые командой сверх своего фонда, учитываются
отдельно и минимизируются (`solve.role_pool = team_borrow`). Такие часы видны в разборе плана
(«Заимствования»), в причинах задач («Часы других команд: …») и в оранжевом риске «Помощь между
командами». Согласованная помощь переносит часы в фонд команды. Строго внутри команд
(`role_pool = team`) завершается одна инициатива из 15 — это показывает стресс-сценарий
«Без помощи между командами».

## 4. Роли, которых нет ни у одного инженера

**Данные.** 665 часов остатка требуют шести ролей без носителей: руководитель проекта (449 ч),
разработчик 1С, специалист поддержки, аналитик 1С, архитектор 1С, специалист поддержки 1С.
Они встречаются в 26 активных задачах из 37.

**Решение.** Эти часы план не ограничивают: работа выполняется вне штата и показывается отдельным
оранжевым риском «Роли вне штата» с часами до конца квартала (`solve.missing_roles = external`).
Прогресс внештатных ролей идёт вместе с работой штата: если штат сделал 40 % своей части задачи,
внештатная часть тоже уменьшается на 40 %. Если считать такие роли блокирующими
(`missing_roles = block`), завершаются 2 инициативы из 15 — это стресс-сценарий
«Роли вне штата не закрыты».

## 5. Трактовка поля `rung`

**Данные.** Значения от 65 до 95; у задач одной инициативы обычно совпадают, но не всегда
(у PRODF-7126 — 88 и 92). Прямого указания на смысл поля нет.

**Решение.** Больше — важнее; rung инициативы — максимум по её задачам
(`input.initiative_rung = max`). Приоритет используется только как второй уровень цели: при равном
числе завершённых инициатив план выбирает набор с большей суммой rung.

## 6. Story Points задач в работе

**Данные.** У MOB-7011 выработаны все 165 часов сметы, у DB-202 израсходовано 77 из 324. Полная оценка
списала бы из ёмкости очки за работу, которой уже нет.

**Решение.** Задача в работе стоит долю оценки, равную доле оставшихся часов
(`input.inprogress_sp = by_hours`). MOB-7011 закрывается в первом спринте без затрат очков и часов.
Правило одно для консоли и сервера. С полной оценкой (`full`) в квартале завершаются 14 инициатив
из 15: Team-Platform получает 45 SP спроса при 43.2 SP за квартал.

## 7. Лимит очков команды

**Данные.** Ёмкость Team-Platform — 7.2 SP на спринт, а в её бэклоге задачи на 8 и 11 SP.

**Решение.** Лимит проверяется в каждом спринте, но задача выполняется долями: в каждом активном
спринте — не меньше 10 % (`solve.min_progress`). Задача крупнее ёмкости спринта растягивается сама,
например 11 SP как 7.2 + 3.8.

## 8. Единица приоритета и правило переноса

**Данные.** Показатель квартала считает только инициативы, завершённые целиком. 80 % работ по каждой
из 15 инициатив — ноль по метрике.

**Решение.** Лестница целей решателя: максимум завершённых инициатив, затем сумма rung, затем
минимум часов, взятых у других команд, затем максимум задач в квартале и как можно более ранние сроки,
затем прогноз для перенесённого (`solve.objective_mode = count_first`). Жертва при нехватке ресурса
выбирается так, чтобы сохранить больше целей; задачи сорванной инициативы, которые всё же помещаются
в квартал, помечаются как задел.

## 9. Идентификаторы из сметы без строки в таблице задач

В исправленной версии датасета смета и таблица задач совпадают. Правило на случай повторения: такие
задачи не планируются и показываются предупреждением.

## 10. Даты квартала

**Данные.** Последний факт в датасете — 26 мая 2026 года (закрытие задачи), последняя строка истории
команд — 18 мая 2026 года.

**Решение.** Планируется ближайший квартал: 6 спринтов по две недели с понедельника 5 октября 2026 года
по 27 декабря 2026 года, прогноз — ещё 6 спринтов. Дата задаётся в конфигурации проекта сервера
(`start_date`); сервер не даёт начать квартал раньше последнего факта в данных.

## 11. Факт спринта

**Решение.** Три равноправных источника:

1. **Обновлённый датасет** — тот же Excel, что и в начале квартала, со срезом на конец спринта:
   статусы, накопленные часы по ролям, новая строка `Team_history`. Главный путь: так выглядят
   данные компании. Образцы — `data/samples/`.
2. **Отчёт команды** — форма или CSV главы: статусы, потраченные часы по ролям, выполненные SP.
3. **Таблица ядра** `sprint, task_id, role, spent_hours, status` — повторяет блок `Spent_time_roles`,
   для работы с ядром из кода.

По задачам, которые есть в датасете, берётся он; отчёт команды — для остальных задач и для SP команды,
если в `Team_history` нет новой строки.

## 12. Зачёт Story Points по факту

**Решение.** SP засчитываются пропорционально прогрессу, отдельного режима «зачёт при закрытии» нет.
Прогресс за спринт — потраченные часы ролей штата к их остатку на начало спринта; до закрытия задачи
накопленный прогресс не больше 90 %, при закрытии засчитывается весь остаток. Команда, сделавшая
спринт ровно по плану, получает 100 %. Подробно — в разделе «Зачёт Story Points по факту спринта»
файла `README.md`.

## 13. Производительность команды после спринта

**Решение.** Ёмкость команды — средняя фактическая производительность по всем строкам `Team_history`,
включая новые, × 0.8. Генератор проверочных датасетов (`orbit/scripts/sprint_dataset.py`) пишет
производительность как среднюю команды × долю выполненного плана спринта: команда, сделавшая свой
план, не меняет среднюю, отставание её снижает. Писать сами SP плана нельзя — ёмкость плана равна
80 % средней, и команда, работающая ровно по плану, «теряла» бы по 20 % за спринт.

## 14. Стабильность пересчёта

**Решение.** После фиксации базы любой пересчёт — по факту спринта, отпуску, согласованной помощи —
идёт с уровнем стабильности: оставшаяся работа раскладывается как можно ближе к прежнему плану.
Цели квартала при этом важнее стабильности: уровень стоит после числа инициатив и суммы rung.
До фиксации базы план каждый раз считается заново.
